# Linode backend + Vercel frontend

The production Compose stack has four services: Go, PostgreSQL, Caddy, and Docker Mailserver. The Next.js site runs on Vercel. PostgreSQL has no published port. Only Caddy and mail ports are exposed; do not publish the Go service directly because production client-IP rate limits trust Caddy’s replacement `X-Real-IP` header.

## 1. Stage before replacing production

Use a separate staging database/volumes and stable custom hostnames, such as `staging.example.com` on Vercel with `api.staging.example.com`, `auth.staging.example.com`, and `mail.staging.example.com` on Linode. Set `DOMAIN=staging.example.com` and `FRONTEND_HOST=staging.example.com`. Keep all browser origins on the same registrable domain so SameSite cookies work. Arbitrary `vercel.app` previews are read-only.

Install Docker Engine, Compose, Git, and ripgrep on the Linode. Copy this repository, copy `deploy/compose.env.example` to `.env` **on the Linode only**, and enter actual values. Use a long URL-safe database password. Keep `.env` mode 0600 and outside version control. Check `docker compose config --quiet` before starting.

DNS:

| Record                    | Value                                                                                                  |
| ------------------------- | ------------------------------------------------------------------------------------------------------ |
| Existing website hostname | Vercel’s project-specific DNS target                                                                   |
| `api`, `auth`, `mail` A   | Linode IPv4                                                                                            |
| AAAA                      | Only if IPv6 routing and mail reverse DNS are configured                                               |
| Root/domain MX            | `10 mail.example.com`                                                                                  |
| Root/domain TXT SPF       | `v=spf1 mx -all` when this is the only sender                                                          |
| DKIM TXT                  | Value generated by the mail server setup tool                                                          |
| `_dmarc` TXT              | Start with `v=DMARC1; p=none; rua=mailto:postmaster@example.com`, verify delivery, then tighten policy |
| Linode reverse DNS / PTR  | `mail.example.com`, with matching forward DNS                                                          |

Adjust SPF for any other legitimate existing senders; do not overwrite an existing mail setup blindly. Linode may restrict outbound ports 25/465/587. Confirm access with Linode before relying on registration/recovery mail: [Akamai/Linode email policy](https://techdocs.akamai.com/cloud-computing/docs/send-email).

## 2. Bring up storage and certificates

```sh
mkdir -p data/mail-config data/caddy
chmod 700 data/mail-config data/caddy
docker compose up -d db caddy
```

Caddy provisions `api.`, `auth.`, and `mail.` certificates. It uses a fixed Let’s Encrypt issuer so the mail certificate path is deterministic. Before starting mail, verify both `.crt` and `.key` exist in:

```
data/caddy/caddy/certificates/acme-v02.api.letsencrypt.org-directory/mail.YOUR_DOMAIN/
```

Mail mounts this **whole directory read-only**, so renewal file replacement is visible. Mail uses `SSL_TYPE=manual`; never mount only individual certificate files. Verify SMTP and IMAP serve the renewed certificate during staging. Reference: [Docker Mailserver TLS](https://docker-mailserver.github.io/docker-mailserver/latest/config/security/ssl/#caddy).

Start the backend, then create the transactional mailbox with an interactive password:

```sh
docker compose up -d --build backend
docker compose run --rm mail setup email add accounts@example.com
# Set SMTP_USER, SMTP_PASSWORD, and MAIL_FROM in .env to that mailbox.
docker compose run --rm mail setup email add postmaster@example.com
docker compose run --rm mail setup config dkim
docker compose up -d mail backend
```

The server authenticates submission over STARTTLS to `mail.DOMAIN:587`, verifying the certificate hostname. `PERMIT_DOCKER=none` prevents trusting other Docker containers as unauthenticated senders; spoof protection restricts sender identities. Incoming port 25 accepts mail only for configured recipients. Port 993 allows the owner to read the transactional mailbox and bounces. Port 587 requires authenticated submission. Configure postmaster and any desired bounce aliases; the envelope sender defaults to `MAIL_FROM`. Queued messages have stable Message-IDs and persistent retry state. SMTP delivery is at-least-once: a crash after remote acceptance can resend a message with the same Message-ID.

Keep `REGISTRATION_ENABLED=false` until you have tested verification, recovery, bounce reception, DKIM/SPF/DMARC, certificate renewal, and delivery to external inboxes. Verify unauthenticated relay attempts to an unrelated domain are rejected. Only then enable registration and recreate the backend.

## 3. Configure identity and Vercel

Google redirect URI: `https://auth.DOMAIN/social/google/callback`.
GitHub callback: `https://auth.DOMAIN/social/github/callback`.
Set each provider’s ID and secret only in the Linode environment. Test cancellation, existing-account conflicts, explicit linking, and owner MFA before launch.

Bootstrap the owner using a private password file temporarily mounted into a one-off backend container:

```sh
docker compose run --rm -v /secure/password.txt:/run/owner-password:ro backend \
  owner owner@example.com 'Chloe' /run/owner-password
```

The non-root backend user must be able to read the file (set its ownership to UID 10001 and mode 0400). Remove the password file, then sign in with the owner password and complete the QR-code authenticator setup. The CLI does not print the factor secret. No frontend owner UID, shared admin secret, or registration setting grants owner access.

Vercel’s project root is the repository root, framework Next.js, build `npm run build`, Node 24. Configure only:

```
NEXT_PUBLIC_SITE_URL=https://www.example.com
NEXT_PUBLIC_API_URL=https://api.example.com
NEXT_PUBLIC_AUTH_URL=https://auth.example.com
NEXT_PUBLIC_READ_ONLY=false
```

Ordinary Vercel preview deployments default to `NEXT_PUBLIC_READ_ONLY=true`; keep that setting. Set it explicitly to `false` only on the stable custom staging domain. Custom staging domains use their matching backend configuration. Never put DATABASE_URL, mail credentials, OAuth client secrets, signing keys, or owner credentials in Vercel.

## 4. Migrate and preserve rollback

1. Back up the existing PostgreSQL database and uploaded media before running new migrations. Preserve the previous Vercel deployment and previous backend image tag.
2. Restore the old database into the new private PostgreSQL instance. The old `content`, `guestbook`, `messages`, and IDs remain intact. Migrations add tables; seed import runs only when the old seed marker is absent. Published/draft JSON, Portable Text, slugs, and references are retained.
3. Copy existing uploaded files into the `backend_data` volume’s `/data/media`. Preserve filenames and ownership UID/GID 10001. Run `docker compose run --rm backend import-media` to register them. Published legacy project screenshots and portraits also remain under `public/images` in the Vercel deployment.
4. Old Firebase sessions are invalid. For each verified legacy guestbook ownership transfer, run `server map-legacy-owner LEGACY_UID ACCOUNT_UUID` in the backend container. This explicit audited mapping never uses email matching. Leave entries unmapped if ownership has not been established.
5. Check `/v1/health`, issuer discovery and JWKS, all project links/images, RSS, sitemap, private drafts/media, publication, schedules, moderation, author deletion, and contact inbox. Test auth from the stable staging domain and both example clients.
6. Back up again, then switch the Vercel production environment/deployment. Do not destroy the previous deployment or backup. Rollback restores matching database/files/keys and the prior backend image; additive schema changes alone do not remove legacy data.

## 5. Backups, restore drills, and keys

From the Linode repository, run `bash scripts/backup.sh`. It briefly stops backend/mail writers, dumps PostgreSQL, archives media and identity keys, mail queues/mailboxes, mail configuration, Caddy certificates, `.env`, and deployment configuration, and writes checksums. Archives contain credentials; permissions are private. Copy backups encrypted to a separate machine or storage destination you control. A second copy on the same Linode is not disaster recovery.

Restore only into an isolated drill deployment first:

```sh
bash scripts/restore.sh .backups/TIMESTAMP --confirm
```

The restore replaces database, backend data, mail data, and saved deployment configuration. Verify counts, a known photograph, a private draft, a pending schedule, an old signed ID token, existing sessions, and mail queue recovery. Preserve the image tag in the backup’s `images.json`; the archive does not contain Docker image layers. Schedule regular restore drills and record the result.

Rotate signing keys with `docker compose exec backend server rotate-keys`, then restart the backend. Previously published public keys remain in JWKS for existing ID tokens. Back up before rotation. Losing `/data/keys/identity.json` invalidates tokens; do not regenerate it during a deployment. Restrict volume and backup access. Credential secret rotation/disabling in the dashboard revokes that application’s existing grants.

## 6. Observe operation

Run `bash scripts/monitor.sh` from your host monitoring system. Inspect `/v1/health`, authenticated `/v1/admin/status`, structured backend errors, pending/failed email jobs, overdue/failed schedules, `docker compose exec mail postqueue -p`, disk space, certificate expiry, and backup age. Never log passwords, authorization codes, refresh tokens, recovery URLs, or private message contents.

Publishing jobs use PostgreSQL row locks and atomic transactions; a second process cannot publish the same schedule twice. Failed validation is retained on the schedule and visible in the dashboard. Email retries use a persistent job table with exponential delays and a failed state after eight attempts. Review failures before requeuing; do not repeatedly send mail to a bouncing account.

## External acceptance gates

The source and local tests can verify protocol behavior, database transactions, rendering, and recovery. Production readiness also requires real DNS, both social-provider credentials, authenticated SMTP delivery, relay rejection, certificate renewal, Linode SMTP access, a production-domain four-container startup, a restore drill on the target host, and a real device OAuth/passkey test. These are not inferred from passing local tests.
